# SQL del Álbum y envío de TierList · 3 de octubre de 2026

El archivo [ComandosSQL.txt](../ComandosSQL.txt) contiene únicamente SQL para el SQL Editor de Supabase: primero la cuota de envío de TierList, después la instalación del Álbum v2 y al final la configuración de **5 cromos por sobre**, confirmada directamente por el usuario. Cuota y Álbum tienen transacciones independientes; una incompatibilidad del Álbum no impide instalar antes la cuota. El tercer bloque se ejecuta después del `COMMIT` del Álbum. No repite el esquema de `CREATE TABLE` que compartiste ni modifica los datos del foro, el ranking, los partidos o Ultimate Team.

Los archivos fueron revisados localmente. **No se ejecutaron en tu Supabase y no hay una instancia PostgreSQL local disponible para comprobar su ejecución.** La instalación revisa el estado real de tu proyecto antes de cambiar permisos o funciones; puede detenerse si encuentra una configuración antigua que necesita revisión.

## Orden de aplicación

1. Ejecuta [album_audit.sql](../supabase/album_audit.sql). Son consultas: muestran RLS, permisos, duplicados, saldos inválidos, ofertas antiguas, funciones y triggers existentes.
2. Resuelve los avisos descritos abajo antes de instalar o reinstalar el Álbum. En especial, revisa la definición de `cancelar_oferta_mercado` y sus instrucciones de cancelación antes de usarlas; verifica después la devolución real de los cromos. Incluye las ofertas vencidas que todavía tengan `estado = 'activo'`. En este proyecto no hay una interfaz anterior guardada en Git para volver a ella automáticamente.
3. Ejecuta el archivo completo [ComandosSQL.txt](../ComandosSQL.txt). No selecciones únicamente las instrucciones `GRANT` o `REVOKE`: los cambios del Álbum forman una transacción.
4. El tercer bloque del TXT configura los 5 cromos por sobre que confirmaste y muestra una confirmación. No necesitas completar otro comando para establecer esa cantidad. Si vuelves a ejecutar el archivo, se restablece intencionalmente el tamaño a 5. Para conservar una configuración distinta que ya hubieras establecido, cambia solamente `cantidad_confirmada smallint := 5` por `cantidad_confirmada smallint := null` antes de ejecutarlo: el bloque mostrará un aviso y no modificará el valor existente. También puedes ejecutar solo el bloque `do $configurar_sobre$ ... $configurar_sobre$;` para configurar sobres sin reinstalar el Álbum.
5. Verifica desde dos cuentas normales: inventario privado, pegar un cromo, crear/cancelar una oferta, aceptar una oferta ajena y abrir un sobre. El SQL Editor usa un rol administrativo; una consulta que funciona allí no confirma los permisos del navegador.

Si la transacción del Álbum falla, sus cambios se revierten; la cuota de TierList confirmada en el primer bloque permanece instalada. Antes de reinstalar usa únicamente las instrucciones de resolución que hayas revisado con la auditoría. No vuelvas a ejecutar el esquema de contexto ni elimines filas para hacer desaparecer el error. [Transacciones de PostgreSQL](https://www.postgresql.org/docs/current/tutorial-transactions.html).

## Cantidad de cartas por sobre

La versión nueva conserva `album_pesos`: añade solamente los cromos que falten con peso 100, sin reemplazar pesos personalizados. Un peso cero desactiva ese cromo. El sorteo ocurre en el servidor y devuelve qué cartas son nuevas y cuáles repetidas, incluso cuando un mismo cromo aparece dos veces en el mismo sobre.

El tercer bloque del TXT es exactamente [album_pack_config.sql](../supabase/album_pack_config.sql). Primero consulta la definición anterior, sin abrir sobres ni modificarla:

```sql
select p.oid::regprocedure as funcion, pg_catalog.pg_get_functiondef(p.oid) as definicion
from pg_catalog.pg_proc p
join pg_catalog.pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.proname = 'abrir_sobre_album' and p.prokind = 'f';
```

Confirmaste directamente que cada sobre entrega **5 cromos**, por lo que ese valor ya está incluido en el bloque siguiente y al final del TXT. La consulta anterior conserva la definición de la función antigua para revisar su implementación; no intenta inferir el tamaño contando sus bucles. La configuración admite entre 1 y 20 cartas.

```sql
do $configurar_sobre$
declare
  cantidad_confirmada smallint := 5;
begin
  if cantidad_confirmada is null then
    raise notice 'Configuración de sobres sin cambios. Revisa la definición anterior de abrir_sobre_album, sustituye NULL por la cantidad real de cartas y ejecuta nuevamente este bloque.';
    return;
  end if;
  if cantidad_confirmada not between 1 and 20 then
    raise exception 'La cantidad confirmada de cartas por sobre debe estar entre 1 y 20';
  end if;
  insert into thc_private.album_v2_config(singleton, cartas_por_sobre)
  values(true, cantidad_confirmada)
  on conflict(singleton) do update set cartas_por_sobre = excluded.cartas_por_sobre;
  raise notice 'Sobres configurados: % cartas por sobre.', cantidad_confirmada;
end;
$configurar_sobre$;
```

Al ejecutar el TXT completo y terminar correctamente la instalación, los sobres quedan configurados con 5 cromos. El inventario, el pegado y el mercado funcionan independientemente de esta configuración. La opción `null` no borra ni cambia un tamaño ya configurado; ejecutarlo con 5 sí establece o restablece ese valor intencionalmente y muestra una confirmación. Si se instala únicamente el bloque del Álbum y se omite la configuración final, una configuración todavía vacía genera `ALBUM_PACK_SIZE_UNCONFIGURED` sin gastar un sobre ni otorgar cartas.

## Qué cambia en el inventario y el mercado

- Cada usuario tiene una fila por cromo. La instalación aborta si encuentra duplicados; no suma ni elimina registros de forma automática, porque el saldo y el estado de pegado pueden requerir revisión.
- `cantidad` cuenta todas las copias, incluida la pegada. Pegar marca `pegada = true` y mantiene la cantidad. El mercado conserva siempre la primera copia para tu colección, aunque todavía no esté pegada.
- Una oferta nueva reserva una repetida sin descontarla al publicarse. Las copias disponibles para intercambiar son `cantidad − 1 − reservas activas`. Aunque la copia reservada siga en la fila del inventario, queda fuera de las disponibles y no puede ofrecerse ni gastarse en otro intercambio. Cancelar o vencer libera la reserva; no hace falta devolver una copia ni modificar el inventario. Para el usuario, esa copia deja de estar disponible igual que en el sistema anterior, que descontaba una copia al publicar y la devolvía al cancelar.
- Hay hasta dos ofertas activas por cuenta y duran tres días. Aceptar transfiere ambos cromos y completa la oferta en la misma transacción. Los bloqueos de ambos perfiles en un orden fijo impiden que dos aceptaciones gasten la misma copia. [Bloqueos de PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).
- Apertura, publicación, cancelación y aceptación usan una solicitud UUID y un recibo privado. Reintentar la misma solicitud devuelve el resultado anterior; cambiar su contenido genera `ALBUM_REQUEST_CONFLICT`. Los recibos no deben borrarse como limpieza rutinaria.

Las ofertas anteriores conservan `version_mercado = 1`; las nuevas usan `2`. Confirmaste que el sistema anterior descontaba una copia al publicar, la devolvía al cancelar y transfería las cartas al aceptar. La instalación **sigue abortando si hay ofertas antiguas todavía activas, aunque hayan vencido**: todavía hay que revisar la implementación real de las funciones y triggers, y comprobar si los saldos son coherentes. No activa ni cancela ofertas antiguas, no hace devoluciones masivas ni reemplaza el código de sus funciones. No se proporciona aquí una cancelación genérica para esas ofertas: primero hay que revisar la definición y las instrucciones de la función anterior, comprobar la sesión y verificar la devolución. Si no puede probarse, revisa las filas y las definiciones del primer paso antes de seguir.

## RLS y permisos

La instalación mantiene las políticas anteriores y añade políticas propias del Álbum, sin sustituir las reglas del resto del proyecto:

- Activa RLS en inventario, ofertas y pesos.
- Limita el inventario a su propietario; permite a usuarios con sesión consultar ofertas v2 vigentes y sus propias ofertas o intercambios completados.
- Retira escritura directa de inventario, ofertas y pesos tanto a nivel de tabla como de columnas. Las modificaciones del Álbum pasan por las cinco RPC verificadas.
- Protege `sobres_disponibles` contra modificaciones directas del navegador, sin impedir que las RPC del servidor descuenten un sobre.
- Revoca la ejecución desde el navegador de las funciones anteriores conocidas, después de comprobar que no queden ofertas antiguas activas. Conserva sus definiciones para revisión; no las elimina.

RLS y permisos de tabla son comprobaciones diferentes. Las funciones del servidor usan `auth.uid()`, comprueban saldos y pertenencia, y fijan un `search_path` vacío. Una política previa restrictiva adicional puede seguir impidiendo una operación: revisa la auditoría en lugar de desactivar RLS. [RLS de Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security), [funciones de Supabase](https://supabase.com/docs/guides/database/functions).

La instalación también se detiene si detecta otras funciones `SECURITY DEFINER` expuestas que mencionen esta economía o las funciones anteriores, firmas v2 inesperadas, o triggers activos desconocidos en inventario, ofertas o pesos. La auditoría muestra sus definiciones; no se eliminan ni desactivan automáticamente. La comprobación textual no prueba que otras funciones indirectas sean seguras: revisa también sus llamadas y dependencias cuando haya RPC personalizadas. Para funciones usadas solamente por un trigger, retirar el permiso de ejecución directa no desactiva el trigger, pero esa decisión debe hacerse después de revisar su función.

## Contrato de las RPC

| Función | Parámetros | Resultado |
| --- | --- | --- |
| `abrir_sobre_album_v2` | `p_solicitud_id uuid` | `success`, `cartas`, `detalles: [{id, isNew, cantidad}]`, `sobres_restantes` |
| `pegar_cromo_v2` | `p_cromo_id text` | `success`, `cromo_id`, `cantidad`, `pegada` |
| `crear_oferta_album_v2` | `p_ofrece text`, `p_pide text`, `p_solicitud_id uuid` | `success`, `oferta_id`, `estado`, `version_mercado` |
| `cancelar_oferta_album_v2` | `p_oferta_id uuid`, `p_solicitud_id uuid` | `success`, `oferta_id`, `estado`, `version_mercado` |
| `aceptar_oferta_album_v2` | `p_oferta_id uuid`, `p_solicitud_id uuid` | Campos anteriores y `cromo_recibido` |

Los errores de negocio incluyen un código estable en `details`: `ALBUM_AUTH_REQUIRED`, `ALBUM_PROFILE_MISSING`, `ALBUM_REQUEST_REQUIRED`, `ALBUM_REQUEST_CONFLICT`, `ALBUM_NO_PACKS`, `ALBUM_PACK_SIZE_UNCONFIGURED`, `ALBUM_WEIGHTS_UNAVAILABLE`, `ALBUM_INVALID_CARD`, `ALBUM_NO_COPIES`, `ALBUM_OFFER_LIMIT`, `ALBUM_OFFER_UNAVAILABLE`, `ALBUM_LEGACY_OFFER` y `ALBUM_BALANCE_PROTECTED`. Los errores de red pueden perder la confirmación de una operación exitosa; por eso el frontend debe conservar el UUID para reintentar.

## Compatibilidad al volver a una versión anterior

El frontend anterior usa RPC que esta instalación retira del navegador. No existe aquí una versión anterior de la interfaz guardada en Git y no se ofrece una reversión automática. Conceder de nuevo todas las funciones tampoco resuelve la compatibilidad: mezclar ofertas antiguas con reservas lógicas v2 puede duplicar o perder cromos. Revisa/cierra las ofertas v2 y sus saldos con el modelo v2 antes de preparar una reversión específica. Las definiciones de las RPC anteriores permanecen en Supabase para revisión, pero no debe suponerse que su interfaz antigua esté disponible.
